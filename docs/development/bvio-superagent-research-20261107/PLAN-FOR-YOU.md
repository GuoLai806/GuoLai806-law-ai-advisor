# bvio 的 OpenViking 与 DeepSeek SuperAgent：这轮调查的结论

**建议保留现在的 RAG 检索主链，借鉴 bvio 的按需阅读和运行管理；Agent 借鉴 DeepSeek SuperAgent 的长期任务管理，继续由 GCode 执行。现在没有数据证明换掉两套内核会更好。**

这轮按你指定的「需求」技能做只读调查、源码核对和小实验，完成文档，没有开始业务开发。你后来纠正了名称，实际对象是 [DeepSeek SuperAgent 研究原型](https://github.com/deepseek-ai/dsh-superagent-prototype)，不是 Superpowers。

本文可以独立阅读。[开发执行版](PLAN-FOR-AI.md)使用同一组决定；[RAG 详细对照](RAG-COMPARISON.md)、[SuperAgent 接入分析](SUPERAGENT-INTEGRATION.md)、[测试协议](BENCHMARK-PROTOCOL.md)给出完整依据。这是一组跨仓库共用文档，两仓库保存同内容镜像，主任务统一维护，以 GCode 入口为权威。

## bvio 和我们的 RAG，实际差在哪

bvio 主要给 Agent 查记忆：先找可能相关的条目，给短预览，Agent 有需要再继续读。我们的系统主要回答资料问题：找文献、拿完整证据、生成答案、核对引用，再让用户打开同版本原文。不能拿“返回预览用了多久”对比“完整回答用了多久”；用户最后是否得到正确答案、总共等了多久，必须另测。

| 环节 | bvio 当前入口 | 我们当前入口 |
| --- | --- | --- |
| 找候选 | OpenViking find/search，可带类型、时间、标签 | OpenViking 实际 find，加 BM25 关键词排序 |
| 合并 | 语义结果和可选字面关键词命中交替选择 | RRF 按名次融合，再由 Qwen 重排 |
| 内容 | 短预览，提示继续读 | 选中完整段落，计算回答输入预算 |
| 原文 | 分页和来源信息 | 原文、段落、hash、引用绑定知识库版本 |
| 主要长处 | 记忆筛选、按需阅读、后台任务管理 | 有同题检索数据，证据和完整回答验收较明确 |

bvio 引擎有更丰富的上下文组装模块，包括类型配额、分层正文、跨轮去重和请求内查询向量复用，但**当前企业 HTTP 入口没有调用这个组装模式**。不能把“代码里有”全部说成“用户正在用”。拿到的也是 48 个相关文件的选择性快照，完整部署与模型配置仍未知。

它还有一个类名带“层级检索”，但固定版本实际是一次全局向量检索，之后可选重排。不能只看名字就认定它逐层查目录，或者因此更先进。

## 测试说明了什么

本轮直接调用 bvio 的真实纯函数，用独立合成文本做了 **14 个边界实验**，保存了[原始观察](evidence/bvio-pure-probe-v2-results.json)。没有启动企业服务、调用模型、写索引或读取企业业务语料。第一版也保留，两版有重复，不能加成 27 个独立实验。

- 1,216 个 JavaScript 字符单位的原文截成 800 后，末尾否定条件消失。它带有继续读的提醒；本轮没执行后续阅读，不能说 Agent 已经误答。
- 两路各限制 2 条时，最后可以返回 4 条。同一个 limit 不代表双方返回数量相同。
- 第一条预览超过剩余预算时，会停止选择，后面放得下的短命中也不再补入。
- 正文预算 100，符合入口标题限制的合成结果 JSON 为 588 字符单位。预算没算标题、URI 和提示；这不是实际模型 token 数。

这些证明了边界，**没有证明问答准确率或系统延迟的胜负**。实验使用本机 Node 26，企业声明 Node 24，也不能据此报告企业正式平台验收成功。48 个企业源文件前后 hash 一致。

我们已有的有效证据是：历史同一批 300 题，关键词检索 nDCG@10 为 0.6689，融合加 Qwen 后为 0.7942，最终 Recall@20 为 93.59%。这支持保留排序链，不能改写成回答准确率。最近 30 题，新回答方式只从 21 题正确变成 22 题，区间仍跨 0，等待也增加。它们是历史实测，不是本轮重跑，更不是与 bvio 对照。

因此，“确认他们更好后照着改”的条件目前没有成立。我没有用预览体积、模块数量或功能测试数量代替性能，也没有据此替换主链。

## RAG 方案如何调整

**先验证连接复用。** 我们每次 OpenViking 查询都会新建 HTTP 客户端，可以改为服务生命周期内复用。有明确源码理由，质量风险较小；节省多少时间仍需测。完整等待可能主要花在重排和云模型上，不能先写“显著提速”。

**再增加可选的资料探索入口。** 先看预览，需要细节再读；正式回答前仍必须拿到完整、可核对的证据，不能用预览当证明。这适合长文和多轮查资料，但节省调用、减少等待的收益尚未验证。

时间、类型、来源过滤和后台入库、索引可见性、停机排空，可以后续独立引入。记忆的跨轮去重不直接套到单次问答：同一文献即使以前读过，这次仍可能是必需证据。查询改写和额外摘要先不开启，避免同时改太多因素、无法解释数据。

下一轮仍是开发 6 题、正式 30 题，不恢复 300 题。完整对照两组各跑 30，失败全留，同题比较。少量长文和取消场景单独验证机制，不混进标准问答成绩。测试协议写明实际后端、冻结、时间、引用、用量、失败和选用条件。

## SuperAgent 值得学什么

它把“收到请求”和“跑一次模型”分开：请求经过规则判断，成为有授权和范围的长期任务；任务可以经历多次执行、暂停、补充输入和恢复。进展、等待人工、可审阅结果、失败有结构化状态；待执行动作和通知存入数据库，重启后可以核对。

GCode 已有执行循环、多 Agent、共享预算、回执、恢复和工作树，最值得补的是“一个需求如何跨多次运行持续下去”。建议第一版只接收你在本机明确提出的任务，用 SuperAgent 的管理思路调度 GCode；GCode 继续负责工具、权限、CU、预算、原始历史和工作树。以后再按明确授权接 GitHub 来源。飞书、自动评论、自动合并和无人值守接单，本轮均不启用。

这是官方组织公开的研究原型。README 明确说不是正式产品，也不等同内部版本或文章描述，不能把公开代码说成已实现文章里的全部 Council/Tape 设计。它依赖 DeepSeek Harness 和 Cordis，不能作为 Python GCode 的普通技能直接导入。原型的 worker 以宿主用户执行，独立目录不等于操作系统沙箱；结合时要保留我们已有的应用层限制。

## 接入前要补的一处缺口

GCode 的普通子任务与技能 fork 路径不一致：技能 fork 新建 Agent 时传入空权限检查器，没有完整继承父权限上限、hook 和共享预算；所谓 full 上下文把每条消息截到 200 字。模型调用的 LoadSkill 直接激活正文，没有按技能 mode 分派。[只读审计](evidence/gcode-skill-contract-v2.json)固定了源码身份和这些事实，未执行越权操作。

下一轮先统一入口，再接任务控制层。所有子执行继承父权限和预算，恢复读真实历史；结果不明的写操作继续停下来核对。否则上层有授权流程，执行时仍可能丢限制或上下文。本轮只把改法写进方案，没修改代码。

# 真正使用 OpenViking 的 RAG：大白话交付说明

先说结论：这一轮已经把5,183篇科学资料实际放进OpenViking，完成300题真实问答流程测试，也实际点过网页上的提问、查看原文和停止。检索成绩有依据：nDCG@10为0.7942、Recall@20为93.59%，同一批问题上比关键词搜索明显改善。但完整问答还没有证据证明达到业界前沿：回答与人工标签一致的有212/300题，引用文档与标签F1为0.5358，完整流程完成269/300题。现在适合在简历上写实际做出的工程和这些明确范围的数字，不能写“全流程SOTA”或“回答准确率95%”。

想看逐项数字，可读[完整结果](RESULTS.md)；想给写代码的Agent接手，可读[执行版](PLAN-FOR-AI.md)。[选型理由](TECHNOLOGY-DECISIONS.md)、[行业参照](INDUSTRY-COMPARISON.md)、[复现步骤](REPRODUCTION.md)和[简历句子](RESUME-REWRITE.md)分别讲清依据。本文可以独立阅读。

原文查看的分工：OpenViking参与实际入库、语义检索及入库回读验收；用户查看原文时，产品接口读取本地Catalog/SQLite的同版本正文并校验hash。每题原文回读不是再次向OpenViking取正文。

## 它现在实际怎么工作

你输入问题，OpenViking先按意思找资料，关键词搜索再补一批。系统按排名把两路合并，让Qwen重排模型仔细比较相关性，最多选4条完整资料交给DeepSeek组织回答。答案带引用，你可以点开同版本原文核对；完成的答案还会保存在自己的会话里。

OpenViking负责资料和向量检索，BGE-M3负责把文字变成能比较的向量，Qwen负责重新排序，DeepSeek负责读资料后回答。OpenViking这次是实际运行的0.5.3服务；5,183篇资料都做过原文回读和检索可见性检查，每道正式问题都走了真实OpenViking。我们没有用预先算好的相似度矩阵替代这一步。

本轮先测完整、长度有限的科学摘要。每篇作为一条完整L2原文存储，没有启用目录摘要或长文自动层级检索。这样便于核对证据是否完整，但它还不能证明复杂PDF、扫描件、OCR、中文长文或多轮追问的效果。

## 300题说明了什么

数据是公开SciFact：5,183篇资料、300个科学论断，标签分支持、反驳和证据不足。它对应BEIR检索test和SciFact公开dev，不是隐藏榜单；这300题以前用于旧参考检索实验，不能说整个项目从未见过。本轮仅用固定32道train开发题选设置，再冻结配置跑300题。正式错题和失败全部保留，没有用它们调设置再替换成绩。

| 实测项 | 结果 | 大白话含义 |
| --- | ---: | --- |
| 检索nDCG@10 | 0.7942 | 相关资料是否排在前面，越高越好 |
| 检索Recall@20 | 93.59% | 前20条找回了多少标注的相关文献 |
| 回答标签一致率 | 70.67%，212/300 | 支持、反驳、证据不足的判断与已有人工标签一致 |
| 三类macroF1 | 0.7396 | 对三种判断分别衡量后平均，减少只看多数类别的问题 |
| 引用文档与标签F1 | 0.5358 | 判断正确且引用的文档也符合标注；是本项目自定义指标 |
| 完整流程完成 | 89.67%，269/300 | 完整答案、引用检查、原文和会话回读走完 |

这几个数字不能混用。找到相关资料不等于理解正确，引用编号存在也不等于每句话都得到文献支持。188道有标注文献的题里，172道最终选入的证据已经覆盖全部标注文献；这172道中仍有19道流程正常但判断错误，另有9道流程失败。

证据不足尤其需要改：112道里只对58道，正确率51.79%。支持题为101/124，反驳题为53/64。不能只展示较好类别，也不能把检索93.59%写成回答准确率。

## 31次失败和等待怎样解释

17题因现有生成门槛只展示资料，没有生成可交付答案；其余14题是生成阶段错误：12次ConnectError、1次RemoteProtocolError、1次TimeoutError。日志能证明错误类型，不能证明是云服务、网络还是睡眠造成的。失败都在300题分母里，不能删除后报成功率。

共有10题发生一次空回答重试，合计293次生成尝试。269题有已报告用量，259题所有已尝试调用都有用量；已知用量总计608,961 tokens。缺报仍是未知，不能把这个数当全部费用。

原始逐题秒表记录的总等待中位30.31秒、95%分位67.11秒，重排阶段中位16.38秒。但这次电脑在运行期间合盖，电源日志记录睡眠约4小时6分；整个运行日历跨度约6小时58分。macOS这次使用的单调时钟不会像日历时钟那样在睡眠中继续推进，所以这两个分位数不能当成真实日历等待，也不能证明持续唤醒服务器的线上速度。质量和失败成绩照实保留，没有为了好看重跑。下一轮速度验收必须让机器持续唤醒，并同时记每题日历时间和单调时钟。

网页另做了三次验收：一次明确只给资料，一次完成回答并打开原文，一次点击停止、看到草稿撤回。它们是功能验收，不加入正式300题质量分数或延迟统计。

## 为什么选这些技术

关键词、向量、融合和重排都是同一批真实请求的实际记录，能够恢复各阶段前20名。关键词检索nDCG为0.6689，OpenViking向量为0.6446，两路融合为0.7043，加Qwen重排后为0.7942。最终比关键词提高0.1253，约18.73%相对提升；按问题重采样的95%差异区间是[0.0922, 0.1591]。这支持这套组合在本数据上的检索选择，不能说回答也提高18.73%。

Qwen和BGE重排最后分别跑了同配置32题，两边标签一致率都为68.75%。Qwen的macroF1为0.5796，BGE为0.5741；引用文档标签F1为0.5138和0.4792。按事先决定的质量优先顺序选Qwen。差异区间都跨0，32题还不足以证明稳定领先；而等待中位39.8秒对17.6秒，速度代价明确。数据尚不能证明微小质量收益值得这份代价，因此下一版仍需比较。

选4条完整证据，是开发集中的相关文献在前4条已有较好覆盖，同时控制生成上下文。它不是所有领域都只需4条的结论。选Pro和较低思考强度、足够输出空间，并只对完全空回答重试一次，是为了解决开发时真实遇到的空输出问题；历史试验同时改过多项条件和代码，不能把全部改善只算给某个模型。

生成门槛本轮固定为0，没有独立标定。不同重排模型的原始分数不是统一概率，这次17题未生成就是必须正视的结果。现在不能为提高完成率临时关门槛。下一版要用开发题比较误放行、误拒绝、判断质量和等待，再冻结选择。

## 距离“前沿”还差什么

本次调查38个公开配置，其中14份与原版SciFact任务和数据版本一致。若只看检索nDCG，本项目0.7942与NV-Embed-v2的0.80111、stella的0.80090、GritLM的0.79129在数值上接近。但外部表多是单个embedding，我们是关键词、向量和重排组合，硬件也不同；它们没有测本项目的答案、引用、会话和失败。只能说同数据集检索数值处在接近这些公开高分配置的量级。

真正需要推进的是证据不足判断、引用质量、门槛标定和完整流程可靠性，再在没有参与调参的新评测协议里验收。扩展通用RAG还需中文、多个领域、长文、无法回答的问题和完整回答强基线。当前结果已经能定位这些问题，比只有一个漂亮检索分数更容易解释下一步开发。

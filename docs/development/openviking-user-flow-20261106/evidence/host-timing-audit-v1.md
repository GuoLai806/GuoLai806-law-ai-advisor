# 本轮主机睡眠与计时差异核对

正式300题的UTC记录为2026-11-06 08:09:36到15:07:29，北京时间16:09:36到23:07:29，总跨度25,073秒（6小时57分53秒）。逐题 `user_total_ms` 的和为10,378.623392秒（约2小时52分59秒），两者差14,694.376608秒（约4小时4分54秒）。原报告SHA256为 `6458c0f67455f94fd740c4eed1e02e7348448fb866383ebc6f29e3c87628b249`。

只读电源日志显示：18:52:19开始合盖睡眠，22:59:43完整唤醒；期间24次Sleep、23次DarkWake、1次完整Wake。将每次实际Sleep配对到下一次实际DarkWake/Wake，并与正式窗口取交集，合计14,756秒（4小时5分56秒）。整个合盖到完整唤醒跨度14,844秒，其中日志状态之间的短DarkWake间隙共88秒；这些间隙没有计入睡眠总数。`Wake Requests`只是唤醒预约，不作为实际Wake。

正式Python 3.12.13的 `time.get_clock_info('monotonic')` 实测实现为 `mach_absolute_time()`。官方CPython同版本源码也使用该调用；本机macOS SDK将 `mach_continuous_time()` 注释为“like mach_absolute_time, but advances during sleep”。本轮每题的秒表使用前者，因此它与跨越主机睡眠的UTC日历等待并非同一个量。

日志估计的睡眠总数比“UTC跨度减逐题秒表之和”还多61.623392秒，不能把全部差额严格等同于睡眠。报告开始/结束还包含题外初始化、健康/身份读取、逐题journal和进度输出等开销，电源状态时间只有秒级，实际硬件挂起与状态日志边界也不是本轮独立测量的量；剩余差额没有被逐项证明。没有逐题UTC开始/结束时间，无法把睡眠精确分摊给某道题，也不能据此把现有p50/p95修正成连续用户日历等待。

最终文档可直接写：**本轮正式运行的日历跨度约6小时58分；期间主机发生约4小时6分的日志睡眠。逐题延迟使用macOS单调时钟统计，主要反映秒表推进时的请求处理时间，不能当成一台持续唤醒机器的生产用户等待指标。质量、失败和原始记录全部保留，延迟数据同时披露这个主机条件。**

本核对不证明ConnectError或其他失败的具体根因，没有把失败归为网络中断、没有删题、没有重跑，也没有修改模型或运行服务。详细24段交集、48条脱敏实际状态行、原行与脱敏行hash、计算方法和时钟依据见 [JSON审计](host-timing-audit-v1.json)。原电源行未复制保存，设备/网络/进程/电量/标识字段均不在交付材料中。

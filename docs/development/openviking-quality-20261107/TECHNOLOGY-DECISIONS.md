# 为什么这样做 RAG：选型理由、实测依据与边界

这版保留真实OpenViking，重点改回答证据表达和交付检查。完整30题对照已结束：标签21→22/30、NEI4→6/10、引用文档与标签F1 .5614→.7143、流程27→29/30；反驳7→6/10、等待和已报用量增加。总体差区间跨0，引用F1差区间碰0，不能写稳定前沿。候选保留可选，默认text不变。

整体决定见[用户版](PLAN-FOR-YOU.md)和[AI版](PLAN-FOR-AI.md)，完整同题质量、失败、等待、用量和区间见[结果](RESULTS.md)。以下逐项区分实测依据、工程起点和收益限制。

## 先把几个数字的意思讲清楚

“找到相关论文”“判断结论正确”“引用文档和判定一起命中”“用户能拿到并打开保存的答案”是四件事。本轮把它们分别统计。

| 基线正式 30 题指标 | 已确认结果 | 能说明什么 |
| --- | ---: | --- |
| 标签一致率 | 21/30，70.00% | 与 SciFact 既有标准标签一致，全部失败仍在分母中 |
| 三类 macro F1 | 0.713247 | 支持、反驳、证据不足各自计分后平均，避免只看一种类别 |
| 证据不足判断 | 4/10；该类 F1 0.533333 | 该类别仍有明显短板；3 道门槛拒绝也在这 10 题内 |
| 引用文档与标签 F1 | 0.561404 | 标签和被引用标准文档同时命中；是项目自定义指标 |
| 检索 nDCG@10 / Recall@20 | 0.864658 / 0.966667 | 排名前 10 的相关文献位置、前 20 对相关文献的平均覆盖 |
| 最终所选证据平均 Recall | 0.833333 | 预算后真正选中的资料覆盖，低于检索前 20 的覆盖 |
| 完整用户流程 | 27/30，90.00% | 答案交付、引用结构、非降级检索、原文回读和完成会话回读 |
| 原文 / 完成会话回读 | 30/30 / 27/30 | 来源仍能打开、完成答案仍能从会话读出 |

引用文档与标签 F1 的正确对数为 16，预测对数为 37，标准对数为 20，precision=0.432432、recall=0.800000。它没有逐句判断每个断言是否被引用句子支持，也不是 SciFact 官方句子 rationale 榜单。

依据为[基线报告](evidence/baseline30-v1.json)、[分析与检索复算](evidence/baseline30-v1.analysis.json)、[原始材料审计](evidence/baseline30-v1.audit.json)。审计通过表示记录、源码、配置、答案提取和时间能对上；它不表示每个答案正确。基线标签一致率的 query bootstrap 95%区间为[53.33%, 86.67%]，小样本不适合宣称稳定领先。

## 1. 保留真实 OpenViking，复用已经验过的索引

用户明确指定 OpenViking，因此正式测试必须真的调用这个后端。项目使用 OpenViking 0.5.3，把 BGE-M3 向量检索放在独立服务中；每题请求实际经过 `/api/v1/search/find`，限定语料与版本 scope，取 L2 资料单元。当前 30 题基线的 trace 和审计确认 30/30 都走实际 OpenViking。

前一轮已经导入并核验 5,183 篇文献，采用 `vectors_only`、`parse_mode=no_split`，保留文档 ID、正文单元和版本对应关系。历史完整导入用时 920.95 秒，逐篇原文回读与可检索性检查用时 121.49 秒。这一轮复用已经验过的 scope 与索引，避免把“换回答策略”的对照同时变成一次向量空间和入库方式的改动；上述入库耗时是历史结果，不能说本轮重新导入又测了一次。

产品打开原文时读取本地 Catalog/SQLite 的同版本内容并核对 hash；OpenViking 原文回读发生在入库验收。不能说网页每次打开原文都会重新调用 OpenViking 的内容接口。

这个选择证明了真实 L2 导入、向量检索、scope/版本隔离和原文定位。没有测试过的 L0/L1 摘要检索、长文层级路由、OCR和多模态能力不计作项目成果；也不把已安装的 0.5.3 宣称成调研日期的全球最新版本。源码依据：仓库 `evidence_rag/retrieval.py`、`evidence_rag/viking_index.py`、`benchmarks/index_openviking.py`。

## 2. BM25 与 BGE-M3 各找一批，再用 RRF 合并

关键词检索擅长术语、名字、编号；向量检索有机会找到用不同措辞表达同一个关系的资料。我们把 SQLite FTS5/BM25 和 OpenViking/BGE-M3 的结果同时保留，再用各路的名次融合。RRF 计算各来源的 `1/(60+名次)` 之和，不直接相加 BM25 与向量的原始分数，因为这些分数的方向和数值尺度不同。

BGE-M3 使用已固定的 1,024 维向量和索引。它是继承已验证配置的决定，不声称是当前最强 embedding，也没有在本轮正式题目上重挑模型。

| 同题检索阶段 | 历史完整 300 题 nDCG@10 / Recall@20 | 当前基线 30 题 nDCG@10 / Recall@20 |
| --- | --- | --- |
| 仅 BM25 | 0.668898 / 0.836556 | 0.716803 / 0.866667 |
| 仅 OpenViking dense / BGE-M3 | 0.644566 / 0.823556 | 0.701922 / 0.833333 |
| RRF 融合，重排前 | 0.704273 / 0.868556 | 0.752049 / 0.900000 |
| 融合后加 Qwen 重排 | 0.794201 / 0.935889 | 0.864658 / 0.966667 |

每列来自各自同一次运行的真实 trace 重建，没有为四种方案分别生成答案。历史 300 题的最终排名相对 BM25，nDCG 绝对差 +0.125303，配对 bootstrap 95%区间[0.092150, 0.159107]；相对 RRF 重排前，绝对差 +0.089927，区间[0.061724, 0.120235]。这是保留融合与重排的可核证依据。

表格两列的题目范围不同，不能把 0.794201 到 0.864658 当作本轮优化带来的提升。当前基线30的高检索分也不证明前沿：没有同条件外部完整问答系统对照，小样本仍有选择与相关性限制。当前 TREC v9.0.8 的独立评分复核在四位小数舍入容差内；这支持指标计算可靠，不支持榜单排名。

源码依据：`evidence_rag/retrieval.py` 中 `rank_candidates/rrf`。历史依据：仓库 `docs/development/openviking-user-flow-20261106/RESULTS.md` 的同题阶段表及 paired 区间；当前依据：[基线分析](evidence/baseline30-v1.analysis.json)的 `retrieval_stage_ablations` 和 `trec_eval`。

## 3. 延续 Qwen 重排：偏质量选择，接受本机等待代价

Qwen3-Reranker-4B 不是因为模型名字新而被选择。历史最后一组同配置 32 题对照，Qwen 与 BGE-reranker-v2-m3 各保留 1 题失败。按预先声明的顺序先比 macro F1，再比引用文档与标签 F1，再比检索排名，最后比等待，选择了 Qwen。当前继续沿用 Qwen、batch8、MPS float16，固定权重 revision。

| 历史最终开发 32 题 | Qwen | BGE 重排器 |
| --- | ---: | ---: |
| 标签一致率 | 68.75% | 68.75% |
| macro F1 | 0.579638 | 0.574074 |
| 引用文档与标签 F1 | 0.513761 | 0.479167 |
| 检索 nDCG@10 | 0.835023 | 0.803544 |
| 用户等待中位数，原单调时钟 | 39.815 秒 | 17.576 秒 |
| 重排阶段中位数 | 19.641 秒 | 1.126 秒 |

差异并不稳：macro F1 差值95%区间[-0.119872, 0.129501]，引用F1差值区间[-0.079199, 0.142780]，nDCG差值区间[-0.001965, 0.079202]，都跨0。因此可以说“依据预定偏质量规则选择”，不能说“统计证明 Qwen 稳定优于 BGE”。

当前基线30的重排阶段中位数为16.922秒，明显大于关键词召回0.358秒和向量召回0.300秒。这说明本机体验优化时，重排阶段值得单独研究；本轮没有在正式运行中换模型、做量化或调 batch 来追分。历史延迟受共享桌面与时钟口径约束，不能包装为生产吞吐。

证据：历史 `TECHNOLOGY-DECISIONS.md/VALIDATION-HISTORY.md`，当前[分析](evidence/baseline30-v1.analysis.json)的 `stage_latency_ms`。权重 revision 分开记：BGE-M3 是 embedding，BGE-reranker-v2-m3 是重排器，二者不混称。

## 4. 用“判定、解释、原文摘录”的 JSON 契约检查引用

候选让同一次模型请求返回三个部分：`decision`、`answer`、`evidence:[{id,quote}]`。程序先检查结构，再把结果渲染成用户能读的文字。未知或重复来源编号、额外字段、重复 JSON key、伪造摘录、不匹配的正文引用都会拒绝。

摘录验证只做一件明确的事：空白规范化后，检查这一段文字是否连续出现在提供的来源标题或正文中。大小写、标点和否定关系不做语义改写。这可以阻止“引用编号有效，但引用句子根本不在原文里”的一类错误，检查是确定性的，也不需要另一次模型评审调用。

它没有证明摘录支持结论。例如原文是“治疗没有改善结果”，摘录可以是真实的，模型却仍可能判成“支持治疗改善结果”。字面存在检查不会独立识别这个语义错误。metadata因此明确写 `semantic_support=model_assessed_not_independently_verified`，不能改写为“独立语义校验”“零幻觉”或“全部断言都有充分证据”。

支持、反驳和普通问答 `ANSWER` 至少要提供一条有效摘录。证据不足可以不给支持摘录；此时显示“参考资料尚不能支持结论”，不把参考来源记成支持证据。科学评分只接受三类科学判定，普通问答 `ANSWER` 可以在产品上完成，但不能靠正文另猜一个科学标签来拿分。

选型的动机来自已测短板：历史300题里，188道支持/反驳题有172道最终证据完整覆盖，但其中仍有19道在无流程失败时判错；当前30基线又只有4/10证据不足判对。找到资料和编号正确都不够。新契约预期让模型更明确检查条件与挑选决定性依据，正式候选引用precision提高、recall降低、NEI多2题、反驳少1题；正确率仅多1/30，具体区间见RESULTS。这个联合策略不是稳定泛化证明。

源码依据：`evidence_rag/grounding.py`、`evidence_rag/answer.py`、`benchmarks/short_protocol.py`。回归检查契约与边界，不能替代人工语义评测。

## 5. 只对通用资料改变生成门槛，并保留预算与降级限制

旧配置要求首条证据的重排分数达到0才生成。相关性 logit 不是“证据充分的概率”，也不等于支持或反驳。当前基线30里，3题因门槛只展示证据，全部属于标准证据不足类；它们没有调用生成模型，被记为未完成和INVALID，不能直接补判成正确证据不足。历史300里也有17题这样的门槛拒绝。

候选的 `grounded_evidence` 只在 `general + grounded_json` 生效，允许模型读到低相关性分数的已检索资料，再输出判定并接受摘录契约检查。仍然要求语料ready、证据存在、没有检索降级、没有适用性待审、预算可验证、没有遗漏证据。法律 profile 保留原来的版本与适用性限制，不因为通用RAG实验而放宽案件结论。

这是一项明确的取舍：预期减少“相关性分数低便无法说明证据不足”的情况；也可能增加模型误把弱相关资料当支持证据的风险。摘录真实并不能消除后一风险，所以必须同时看NEI、标签、引用质量、完成率和失败，而不是只看完成率。

本轮同时改变回答格式、附加提示契约和交付门槛。候选如果改善，应称“这组grounding策略在这30题对照上的变化”，不能将收益全部归因于JSON、某句提示词或关闭零阈值中的一个因素。源码依据：`evidence_rag/api.py` 中 `may_generate` 与 runtime identity。

## 6. 保持一次生成调用，只有完全空正文才最多重试一次

没有加一个“评审模型再判断一次”或“模型自己修JSON”的循环。正常路径只有一次上游生成请求。grounded模式缓冲到成功终止后统一验证，再交付可读答案；模型身份、尝试与用量事件仍及时保留。用户等待中的正文不是假装逐字流出，一次性可读正文意味着“首个可见答案”可能接近完整回答结束。

保留历史明确的空输出故障处理：第一次未产生任何正文，且属于超时、长度耗尽或缺少成功终止标志等符合规则的情况时，用相同模型和证据关闭thinking再试一次，最多45秒、2,048输出token。主请求thinking enabled/low、最多60秒和8,192输出token。没有第三次尝试。

非空却格式错误的JSON、部分回答后失败、非法引用、连接故障、内容限制和用户取消不触发这个空输出补救。它是避免“思考耗完而无正文”的有限恢复，不是挑两次里分数更好的答案。当前基线30有1题重试，总共28次生成尝试，27题报告usage、26题各尝试usage齐全；缺报仍为未知，不能填0。历史300是10题重试、293次尝试、269题usage可用、259题尝试用量完整。

因此“一次调用”要写成“正常单调用、限定空输出最多一次补救”，不能无条件写“每题仅一次”。用量、等待和失败都应包含恢复尝试。云模型别名不等于固定权重，保存实际返回model与fingerprint，不承诺逐字重现。

## 7. 64 KiB、4条摘录、12–1,200字符都是工程起点

这些常量有明确用途，但目前没有参数扫描证明它们最优。

| 边界 | 为什么先这么定 | 证据与不能外推的地方 |
| --- | --- | --- |
| JSON正文最多64 KiB UTF-8字节 | 给短解释与最多4段摘录留空间，限制异常输出的缓冲内存；超限清空缓冲，继续读到终止以保留usage后拒绝 | 源码和边界回归证明执行上限；未用64/128/256KiB对照证明质量最优。它也不是模型token上限 |
| 最多4个来源，每个ID一次 | 与本轮最多4条完整证据一致，鼓励只给最小充分来源集合，减少堆砌重复引用 | 历史32开发中的25道有gold证据题，在所检查排序里前4和前8均完整覆盖；仅说明当时排名覆盖，不证明所有领域4条足够 |
| 每条摘录12–1,200字符 | 下限减少只截一个词或标题片段的空泛引用，上限控制单段展示与结构解析规模 | 按空白规范化后的字符计数，中文和英文token成本不同；没有语言分层、阈值寻优或语义充分性证明 |
| 完整证据预算6,000 token，4条完整单元 | 保留可定位的完整来源，配合32,768窗口、512包装预留、8,192输出预留 | 实际使用固定tokenizer计量，不靠字符估算；当前基线预算后覆盖只有0.833333，不能用前20 Recall0.966667替代 |

如果未来业务需要更长文档，应在新的开发协议中测覆盖、无法回答判断、引用可读性和等待，再冻结新常量。不能在本次正式30的中途换阈值，也不能把可配置边界描述成经过大规模最优验证的技术结论。

## 8. 用6题开发、30题正式固定对照，完整保留公开已见限制

这是用户确认“改成现在十分之一”的结果。正式从原test来源按支持/反驳/证据不足各10题取30题；开发从train来源各2题取6题。固定种子 `20261107`，按SHA256(种子+题号)选成员并排序，避免按模型表现挑题。旧300清单、标准答案和失败记录保留。

这是公开、已在历史项目中涉及的题目来源。即使这一次的配置没有根据正式30结果调参，也不能称“完全没见过”“隐藏测试”或“无污染”。三类均衡有利于观察NEI，但整体一致率适用于这组10/10/10的组成，不是线上类别分布下的准确率。

6题开发用于发现流程和评分缺陷、冻结候选配置，不能提供稳定优劣结论。早期开发v1/v2记录在评分和失败元数据修复前，主任务保留它们；v3在已确认代码缺陷修复后同策略复核，模型、提示和索引参数没有正式题驱动调优。不能用修复后结果覆盖原失败或挑历史最好的一次。

正式两套各30，同query配对，失败保留分母。最终比较应同时给标签、NEI、引用、完成、等待、用量、区间与个体转移；使用Wilson区间、paired bootstrap与exact McNemar时也要说明样本小、同论文题可能相关、单次云生成未测重复波动。统计方法不能把这30题变成所有通用RAG场景的泛化证明。

## 9. 在任何正式请求前冻结整套证据，并由运行和审计双重核验

只保存两个配置hash不够：人可以手写hash，却没有完整开发依据。现在两份selection互相引用并保存共同摘要，绑定语料manifest、源码、配置、实际运行身份、正式输出路径、开发6报告及原始journal。候选正式配置必须与开发6完全一致；两正式配置除了已声明的联合grounding策略外必须一致。

任一正式报告或journal存在时，冻结工具拒绝重新冻结；正式runner又会检查冻结时间、输出路径与完整pair；审计重读原始证据，检查是否与冻结材料一致。开发真实失败不因数量或低分被自动否决，也不改判为NEI。旧baseline可以不单独开发6，文件明确声明沿用历史text+threshold0且无这次开发调参，共享候选开发记录只作完整性依据。

本轮基线30实际绑定manifest摘要 `8ee8fd71…`、config摘要 `a577eb68…`、pair摘要 `d27ddfad…`，审计中`complete_frozen_protocol`为true。摘要只能约束被记录材料的一致性；云服务别名、共享硬件和网络不是密码学冻结的，因此仍需披露实际环境和生成波动。

源码依据：`tools/freeze_short_run.py`、`benchmarks/short_protocol.py`、`tools/audit_user_flow.py`。这套措施保证“分数来自哪一版、哪些题、怎样运行”可追溯，不保证分数一定好看。

## 10. 日历与单调时钟同时记，再独立从原始快照重建

历史300轮的UTC总跨度约6小时57分53秒，其中系统电源日志与窗口相交的Sleep约4小时5分56秒。macOS的`mach_absolute_time()`与包含睡眠的日历等待不同；历史没有逐题UTC快照，不能把旧p50/p95自动修成连续日历等待。这是本轮必须补双时钟的具体证据。

每题、每个SSE事件现在保存UTC/ns、原有单调耗时、日历耗时和两者差值。缺失就记未知；倒退保留有符号观测并标异常，质量题不删除。独立审计不调用runner的计时辅助函数，从原始快照重建事件顺序、开始结束、首个答案、stream/user wall耗时、分位数和异常计数，降低“报告和检查复用同一错误公式”的风险。

当前基线30的日历总跨度为849.187秒，单调总跨度849.121秒，差66.002毫秒；所有30题wall时钟有效，没有回退或大于1秒的双时钟差异flag。按runner既有离散排序分位规则，全部30题实际wall等待p50=25.699秒、p95=35.243秒，首个可见答案有27个测量。analysis里另存NumPy线性插值的单调分位数，不能把两种算法的结果混在一张前后表里。

UTC的9位小数是格式与原始ns存储精度，不是时钟准确度；本机wall clock报告分辨率约1微秒。1秒差异门槛只是诊断flag，不是性能门槛，更不自动证明睡眠原因。这仍是一台共享桌面、串行客户端和云接口的运行，未测并发容量；比较速度时还要披露两组串行缓存与网络条件。

依据：[基线报告](evidence/baseline30-v1.json)与[审计](evidence/baseline30-v1.audit.json)，仓库 `tools/audit_flow_timing.py`，历史 `evidence/host-timing-audit-v1.json`。该重建是独立代码路径的材料审计，不是人工语义审查。

## 12. 默认仍用text，保留一条简单可执行的回退路径

新JSON与grounded门槛是明确启用的配置。默认`text + reranker_threshold`维持既有文字回答契约，法律profile维持原约束。这样候选不合适时可以按operator配置切回旧行为，不必改库、重建索引或覆盖语料版本。

回退依据是旧baseline仍经过完整正式30，且历史300材料保留；不是认为新策略一定失败。候选若没有改善、格式拒绝增加或等待不可接受，应如实报告，不能在本轮正式冻结后再改配置重跑挑最好一次。发生新的确定代码缺陷，应记录新版本、新run_id与修复理由，保留本轮原材料，由主任务按协议决定下一轮。

## 最终选型结论与材料入口

保留OpenViking及既有检索链，因为用户明确要求且已有真实入库/检索/版本证据；保留Qwen作为本轮偏质量配置，同时承认速度代价和历史差异区间跨0。新grounded模式保留可选，默认继续text。该轮联合策略减少引用堆砌和gate无答案，但牺牲部分引用覆盖、反驳正确题，且等待增加。

同算法wall p50/p95：baseline25.911/38.002秒，candidate29.396/52.712；已报tokens59727→89321，baseline另有缺报及更高缓存命中，不能作总费用比较。60题时钟都有效；身份字段未变，raw后端快照的load_seconds差异保留。安装产物真实API与UI通过，依赖复用范围明确，生产/新机完整依赖/广泛GUI未验。

当前baseline节的指标、离散分位数用于描述基线，不与candidate NumPy分位混用；正式比较一律读RESULTS与paired文件。[原始hash及数字](evidence/README.md)、[复现](REPRODUCTION.md)、[验收历史](VALIDATION-HISTORY.md)均使用仓库相对路径。公开报告不是全部原始正文，原始SSE在本机核验，公开数字可以复算。未经验证常量最优、L0/L1、多模态、成本改善、稳定行业前沿仍不成立。
